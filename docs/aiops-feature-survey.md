# AI 运维系统功能调研：从 Keep 和 OpenSRE 看

> **调研方法**：直接读两个开源项目的源码，不是官网/README 的营销话术，逐条核实"文档里说的功能"是不是真的落地了。
> **调研对象**：`keephq/keep`（本地 `/Users/leishaohui/Desktop/zyl/keep-main`）、`opensre`（本地 `/Users/leishaohui/Desktop/zyl/opensre-main`）。
> **日期**：2026-07-03。

---

## 一句话定位

- **Keep**：告警管理 + 规则/工作流引擎为核心，AI 是叠加在确定性系统之上的辅助能力，且不同 AI 功能之间成色差异很大。
- **OpenSRE**：LLM Agent 驱动的事件调查助手，以读为主、写极少，确定性算法只在个别角落（比如置信度打分）出现。

两者代表了"AI 运维"这个大类下两种截然不同的设计哲学。同一个"功能模块"，在两边的实现深度可能天差地别——这份文档按模块拆开，逐个说清楚"这两家怎么做的、做到什么程度"，最后给 AIOps 自己的路线提几点启发。

## 功能清单速览

| # | 模块 | Keep | OpenSRE |
|---|------|------|---------|
| 1 | 数据接入与集成 | 129 个 provider，读写合一设计 | ~96 个 integration，以读为主，写能力被显式收窄 |
| 2 | 告警去重与关联 | 有，规则引擎（CEL + 拓扑），无 ML | 无这一层，直接从"已有事件"开始调查 |
| 3 | 根因分析 | 弱（只做事后聚类归因），非单事件诊断 | 有，ReAct 循环 + LLM 自评置信度 |
| 4 | 知识与记忆 | 无 | 声称有知识图谱/RAG，实际只是聊天记录持久化 |
| 5 | 自动化执行/自愈 | 真实存在且**无审批网关**（安全隐患） | 写能力窄，但审批字段也**未生效**（同类隐患） |
| 6 | 事件生命周期管理 | 完整的状态机 | 无 |
| 7 | Agent 编排架构 | 不涉及（规则引擎为主） | 已从图框架迁移回顺序 pipeline + ReAct 循环 |
| 8 | AI 能力分级 | 同一产品里从"企业版专享"到"死代码"都有 | — |

下面逐条展开。

---

## 1. 数据接入与集成（Integrations）

- **Keep**：129 个 provider，覆盖可观测性（Datadog/Prometheus/Grafana/…）、工单（Jira/ServiceNow/…）、事件管理（PagerDuty/…）、IM（Slack/Teams/…）、云平台（AWS/Azure/K8s/…）、LLM 后端、数据库等。每个 provider 常见"`query`（读）+ `notify`（写）"双能力设计，同一个 provider 往往既能查数据也能触发动作。
- **OpenSRE**：~96 个 integration，绝大部分是**只读**诊断客户端（查日志、查指标、查慢查询、查副本状态）。写能力被显式收窄到白名单（issue 创建、发消息、代码 diff 生成），且部分需要专门的环境变量开关才能启用。

**我的看法**：读写要不要合并到同一个 provider 抽象，是个真实的设计分叉。合并（Keep 的路子）复用度高，但容易在"只是想读"的场景下不小心带上写的心智负担；拆开（OpenSRE 的路子）更安全，尤其适合"AI 主导决策"的场景。AIOps 目前 servers/日志/告警这几个工具都是纯读，等阶段5接 SSH 执行这种真正有破坏力的写工具时，值得专门划一条"读工具"和"写工具"的边界，不要混在同一个抽象里。

## 2. 告警去重与关联

- **Keep**：去重是哈希比对——排除时间戳等字段后算 `sha256`，跟上一条同指纹告警比对。关联走两条独立路径：一条是 CEL 规则（`definition_cel` + `grouping_criteria` + `threshold`），一条是纯拓扑（同一个 Application 下的服务告警自动合并）。**全程没有 ML**。
- **OpenSRE**：没有这一层——它是"来了一个事件之后去调查"，不负责从海量原始告警里筛出"这是不是同一件事"。

**我的看法**：这是一个容易被"AI 运维"的名头带偏的地方——业界最成熟的开源实现（Keep）在这一步用的是纯规则引擎，不是 LLM，也不是 ML 异常检测。规则/CEL 表达式够快、可解释、好调试，让 LLM 判断"这两条告警是不是一个事儿"反而是杀鸡用牛刀。AIOps 阶段5做告警接入时，去重/关联这层应该老老实实写规则。

## 3. 根因分析（RCA）

- **OpenSRE**：核心是 ReAct 循环（LLM 决定调用哪些诊断工具 → 并行执行 → 循环，直到 LLM 认为够了），最后一次结构化输出把自由文本诊断解析成 `root_cause`/`causal_chain`/`validity_score`。**`validity_score` 是 LLM 自己估的，不是算出来的**。有一个例外：`upstream_correlation` 模块是真的确定性算法（时序趋势相关性 + 拓扑邻接 + 周期性，加权算出置信度），但只用于给候选上游服务排序，不是主 RCA 引擎。
- **Keep**：没有针对单个事件的 RCA 模块——它的"AI 根因报告"其实是把最近 40 个 incident 丢给 GPT 做聚类总结，回答"最近这段时间最常见的故障原因是什么"，是统计归因，不是对某一次事件的诊断推理。

**我的看法**：这印证了 AIOps 阶段4 的设计方向——`plan → execute → reflect` 这种显式多步循环，比一次性把数据甩给 LLM 要更可控。"validity_score 是 LLM 自己说的"这点值得警惕，AIOps 以后如果要展示"诊断置信度"这类数字，要么找到确定性的计算方法，要么老实标注"这是模型自评，仅供参考"，不要包装成看起来客观的分数。

## 4. 知识与记忆

- **OpenSRE**：文档/命名里明确提到 "episodic memory" 和 "Neo4j 知识图谱"，但代码里**都不存在**——依赖列表里没有 `neo4j`、没有任何向量库；"记忆"实际上就是把每次调查的 session 存成 JSONL 文件，支持 `/resume` 接着聊，**没有任何跨 session 的语义检索或"举一反三"能力**。
- **Keep**：没有这个维度的功能。

**我的看法**：这是这次调研里最值得记住的一条——"知识库/RAG"听起来是 AIOps 系统的标配，但连一个专门标榜"AI SRE"的开源项目，实际的"记忆"也只是聊天记录持久化。说明这块工程量比想象的大，市面上"号称做了"的项目大概率也是半成品。AIOps 目前也还没做这块（技术栈里写的是"向量存储后期再决定"），不用因为看到别人"好像有"就觉得自己落后——等阶段0-4的手感打好、真的需要跨对话/跨事件检索时再决定要不要做，是合理的节奏。

> **2026-08-13 更新**：AIOps 已实现第一版跨会话 Agent memory，包括稳定事实抽取、按键合并、相关性检索、遗忘 API 和 PostgreSQL LangGraph checkpoint；当前检索仍是关键词评分，尚未实现本文所说的向量 RAG、知识图谱或 runbook 检索。设计见 [`agent-memory-design.md`](agent-memory-design.md)。

## 5. 自动化执行 / 自愈——本次调研最大的收获在这里

- **Keep**：**真枪实弹**。K8s provider 能 `rollout_restart`、删除重建 pod、`cordon/drain` 节点（drain 甚至有个绕过 PodDisruptionBudget 的强制选项）、任意伸缩、在运行中的 pod 里 `exec` 任意命令；SSH/Bash provider 直接执行任意命令。**整个工作流引擎的执行链路里，没有找到任何审批/二次确认机制**——条件一满足就直接调用动作，失败重试不等于执行前确认。
- **OpenSRE**：写能力被严格限制在小范围（issue/消息/代码 diff），**没有任何基础设施变更工具**（不能重启、不能扩缩容、不能改配置）。但有个更隐蔽的问题：代码里有个 `requires_approval` 字段，标在发消息、改代码这些工具上，但实测确认——**这个字段被声明了，却没有任何代码真正读取和执行它**，是个"声明了安全机制但没接线"的活生生案例。它还有个叫 `guardrails` 的模块，名字听着像"动作审批网关"，实际上是敏感信息脱敏（DLP），跟"能不能执行这个动作"是两回事。

**我的看法**：这两个案例合起来是个很好的反面教材——"看起来有安全机制"和"真的生效的安全机制"是两回事，容易在命名和字段设计阶段就埋下隐患（`requires_approval`、`guardrails` 这类名字会让人误以为它在生效）。AIOps 的 CLAUDE.md 安全红线（破坏性操作必须人工二次确认）比这两个项目的开源版本定得都严格，这不是过度谨慎，是踩在了这两个真实项目暴露出的坑上——写阶段5 SSH 工具时，"审批"要有真实的代码路径（比如卡在一个等待用户确认的状态），不能只是工具描述里写一句"这个需要审批"就算完事，最好专门写一条测试验证"没人工确认，这条路径就是走不通的"。

## 6. 事件生命周期管理（Incident Lifecycle）

- **Keep**：这块做得相当完整——`FIRING/ACKNOWLEDGED/RESOLVED/MERGED/DELETED` 状态机、`is_predicted`（算法生成 vs 人工创建）、`is_candidate`（等人工确认，有专门的确认端点）、`incident_type`（MANUAL/AI/RULE/TOPOLOGY 分类溯源）、事件合并/拆分、跨时间的"这个事件是不是历史上出现过"关联链。
- **OpenSRE**：没有这个概念——它面向的是"来一个事件、调查一次、出个报告"，不负责事件本身的生命周期管理。

**我的看法**：这是之前给 AIOps 画的"数据接入 → 检测 → 诊断 → 执行"那条流水线图里漏掉的一环——"发现了异常"和"这个事件现在处于什么状态、被谁认领、后来怎么样了"是两件事。AIOps 现在还早不用做，但值得记一笔：等阶段5-6 涉及真实告警时，`alert_events` 表大概率需要一个类似的小状态机，而不只是一条平铺的告警记录。

## 7. Agent 编排架构：不是所有"AI Agent"都需要图框架

这是本次调研最出乎意料的发现：OpenSRE 自己的开发文档承认——项目**主动移除了图/链框架层**，现在的调查主流程就是一串普通 Python 函数顺序调用（`解析集成 → 提取告警 → 规划动作 → 收集证据 → 诊断 → 交付`），复杂的"多步骤"其实是里面一个 ReAct 循环（LLM 调工具 → 并行执行 → 循环），不是图的分支/合并。宣传中提到的"并行子 agent"，实际上是"一次 LLM 回复里的多个工具调用用线程池并发执行"，不是好几个独立的调查在同时跑。

**我的看法**：这对 AIOps 阶段4 的选型是个很好的印证——图/状态机（LangGraph）在"步骤会分支、需要回头重试、要持久化状态"的场景下确实有价值（AIOps 自己 `plan → execute → reflect` 带重试这个场景就用得上），但如果只是"顺序执行 + 循环调工具直到完成"，一个手写的 ReAct 循环可能更简单、更好调试、更少踩框架的坑（这次实现过程中，咱们自己也确实在 LangGraph 的一些 API 细节上摔过跟头）。选型要匹配实际的控制流复杂度，不是框架越"重"越好。

## 8. AI 能力的"含金量"分级——Keep 是个好案例

Keep 的宣传把"AI-powered correlation and summarization"作为卖点，但实测代码后发现这句话背后是四种完全不同成色的东西：

| 功能 | 开源版有没有 | 实际情况 |
|---|---|---|
| 全自动 AI 关联 | ❌ 企业/云版专享 | 开源代码里完全不存在 |
| 半自动 AI 关联（建议 + 人工确认） | ✅ 标注"experimental" | 真实可用：单次 LLM 调用把 ≤50 条告警聚类成候选事件，**人工在界面里确认后才真正生效**，用户的调整还会被记录用于后续反馈 |
| AI 根因报告 | ✅ 但没大肆宣传 | 真实可用，对近 40 个 incident 聚类总结高频原因 |
| AI 摘要 | 字段/函数都在 | **实测确认没有任何代码调用它，是死代码** |

**我的看法**：这张表本身就是一个提醒——"AI 加持"四个字可以从"完全没做"横跨到"生产可用"整个光谱，写文档、做汇报的时候最好也用类似的颗粒度区分清楚，别笼统地说"用了 AI"。同时，Keep 那个"半自动关联"的设计（AI 出草稿 → 人工确认才生效 → 修改结果被记下来当反馈）是个值得借鉴的模式——AIOps 场景里，这个闭环比"AI 直接自动执行"更符合安全要求，AIOps 阶段6 多 Agent 协作时可以参考这个交接方式设计 Diagnostician/Executor 之间怎么移交。

## 给 AIOps 的几点启发（汇总）

1. **去重/关联用规则引擎，不用 LLM**——CEL 或等价的规则表达式，快、可解释、好测试。
2. **读写工具分开设计**，尤其是阶段5要接 SSH 这类真正有破坏力的工具时。
3. **"人工二次确认"必须是真实代码路径**，不能只是工具描述里的一句话或一个没人读取的 flag——这是本次调研里两个项目都没做好、AIOps 自己反而定得更严格的地方，要言行一致地落地，最好专门写测试验证。
4. **知识库/RAG 不用因为"别人好像有"而焦虑**——目前看到的两个项目里真正做出向量检索/知识图谱的一个都没有，工程量比宣传的大得多。
5. **图框架不是必选项**，选型要看控制流复杂度：分支/重试/持久化多的场景适合 LangGraph，纯顺序 + 循环调工具的场景一个手写 ReAct 循环可能更简单。
6. **事件生命周期管理是独立的一块功能**，跟"检测到异常"和"诊断根因"是分开的关注点，等做到告警接入时值得单独设计一个小状态机。
7. **"AI 加持"要分级说清楚**——从"完全没做"到"人工确认后生效"到"全自动"，参考 Keep 那张分级表的颗粒度。
